### 1. B2：读端 last-row-wins 与修复对账 `setMaxTotal` 是否两套口径

**是两套口径，但用途不同、不互相矛盾。**

读端（展示真值，`src/lib/local-api.js:202-211` + `src/lib/async-queue-reader.js:49-57/86-91`）：

```js

  label: "readQueueData",

    return { key: `${row.source || ""}|${row.model || ""}|${row.hour_start || ""}`, row: normalizeQueueRow(row) };
```

对账端（修复守卫，`src/commands/sync.js:6585-6589`）：

```js
function setMaxTotal(map, key, total) {
  if (!key || !Number.isFinite(total)) return;
  const prev = map.get(key);
  if (!Number.isFinite(prev) || total > prev) map.set(key, total);
}
```

用途（唯一调用族，`sync.js:5848-5879`，codex rescan/fork 修复的「数据丢失守卫」）：把「现有队列 + 游标态」与「重建结果」各按 **MAX** 汇总后比较，`rebuiltTotal < existingTotal` 且项目侧也降低 → **跳过本轮修复**（`return false`），宁可欠修不可删史。`setMaxTotal` 还经 `mergeMaxTotals`(:6574-6583) 跨两个来源取 MAX。

为什么两套：队列行是「累计快照序列」，展示取最后一行即当前真值；而撤回（零值行，:3376/:19988/:5207）会把最后一行压成 0——若守卫也用 last-wins，历史峰值就被「撤回动作」抹掉，会误判为「无丢失」从而放行原子重写。用 MAX 是刻意的保守方向：**MAX 用于门禁，last-wins 用于展示**。两者读同一份文件但从不互相写回，因此不会产生数据矛盾；唯一后果是撤回历史会让守卫更容易跳过修复（欠修，而非错修）。分片 S4 正文没有出现 `setMaxTotal`（它属于 S2 的论述），§1.3 的「唯一合并规则」只对展示链成立——**建议 S4 在 §1.3 补一句口径边界**。
