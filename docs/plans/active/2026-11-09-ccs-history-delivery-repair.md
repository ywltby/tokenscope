# CCS 历史补充与来源选择交付修复计划

> 执行模型：使用 executing-plans 技能逐项实施。
> 状态：设计完成，待执行；本文件不代表产品修复已交付。

**Goal:** 补齐遗漏的 CCS 来源选择修复，验证会话删除后的已导入历史仍参与统计、重复导入幂等，并明确安装包实际包含哪些修复。

**Architecture:** 复用 PR #56 的桶级三向选择，在当前 main 上整合复验。事实保存、请求身份与统计选择分层；真实数据只读审计，产品查询与导入写入验证使用隔离副本或合成数据。

**Tech Stack:** Rust、SQLite、Vue 3、TypeScript、GitHub Actions。

- 按现有代码与真实库独立核算，61个无明细桶包含24,100次请求、4,337,748,027 token，选择CCS汇总补充。这是只读核算，尚未执行真实副本的产品查询。

根因是来源选择缺少“明细已足够，优先明细”分支，以及已有修复漏发。证据不支持“真实数据已被清坏”。

## 2. 设计与不变量

选择复用#56并更新到当前main，不重建统计体系。直接合并过期分支会带入过时版本/发布声明，必须先整合。清库重建、强制重导、逐字段取最大均不采用。

桶键沿用 `(来源自然日, Claude应用, 等价模型)`；现有时区和时间范围限制保持。

| 条件 | 选择与结果 |
| --- | --- |
| 无请求明细 | 用CCS日汇总补历史；源会话删除不影响已导入事实 |
| A：快照范围内明细请求数及四桶均≥汇总（含相等） | 优先明细，汇总不追加；保留项目/时间/请求级费用，不产生未使用汇总的冲突或边界提示 |
| B：明细请求数及四桶均≤汇总且不全等 | 汇总补足该范围，覆盖明细不再重复计入；可信边界之后的新请求照常计入 |
| C：请求数或四桶方向交叉 | 保留明细回退，明确统计冲突类型；不相加、不造差额、不掩盖可能少计 |

- A/B是来源选择策略，数值大小不证明两边是同一请求集合。CCS从会话文件读取，与是否使用路由无关。
- 日粒度费用未知不等于token未计入；不得将汇总伪造成逐请求明细或项目归属。
- 新查询规则必须直接适用于已有导入数据，不要求重导才修复提示。
- 同内容重导不得增加请求/token/事实，不移动批次归属，不伪造旧边界。来源内容改变且用户选择替换时，内容和批次绑定同事务更新。
- 来源删除、停用、重扫不删除历史；保留当前main的Claude/Codex身份修复与幂等性。
- 不扩展/btw、其他agent、自动CCS同步、测试权限或收费规则。

### T03：界面与真实副本对账

文件：`frontend/src/types.ts`、`composables/useUsageQuery.ts`、`components/UsageTable.vue`、`lib/locales/{zh-CN,en-US}.ts`及对应测试。

2. 原库只用SQLite `mode=ro` + `query_only`审计，不导入、不迁移、不checkpoint、不启动用户实例。
3. 使用SQLite backup API从只读连接取得一致副本，不能只拷贝可能遗漏WAL的主文件。所有业务写入、缓存、价格文件都指向本次独占隔离根；产品查询禁用真实来源发现，不扫描真实会话。
