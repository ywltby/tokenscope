## 任务 B：§4.5(a) 修正判定

**判定：修正方向成立，但"测试本身就在证明这一点"这句偏强，应改述。**

逐行核对 `pricing.rs:4931-4955`：

1. `:4933-4934` 先取 `sonnet_4 = find("claude-sonnet-4-20250514")`、`sonnet_45 = find("claude-sonnet-4-5-20250929")`。
2. `:4936-4943` 的两条 `assert_eq!` **左右两侧是同一表达式**（`find(X).input` 与 `sonnet_X.input`，而 `sonnet_X` 就是 `find(X)`），属**恒真断言**，不携带任何信息。
3. `:4944-4950` 是**唯一有信息量**的断言：`find("anthropic.claude-sonnet-4-20250514-v1:0").input == sonnet_4.input`。
4. `:4951-4954`：`find("claude-3-5-haiku-20241022").input == 0.8e-6`（本条只断言取值，与路径无关）。

对照任务要求的三点：

- 「断言的是两者 input 相等，而非断言裸键存在」——**成立**。全测试段**没有** `find_exact(...)`、`entries.contains_key(...)`
  之类的裸键存在性断言；`unwrap()` 只要求 `find` 返回 `Some`，精确与模糊两条路径都能满足。
- 「测试本身就在证明这一点」——**偏强，建议改述**。该测试对"裸键是否存在"**零信息量**：
  "两个查找名拿到同一个价"在「裸键精确存在且价恰等于 Bedrock 键」与「裸键缺失、模糊落到 Bedrock 键」
  两种情形下**都能通过**。真正区分二者的是本轮的键集证据（真实产物里该裸键**不存在**），而不是这个测试。
  另需注意测试名后缀 `_exactly` 容易被读成"精确命中"，实际语义是"解析到精确相同的价"。
- 任务提示的「是否还有别的含义」——有：前两条恒真断言的外形（"裸名 vs 变量"）容易被误读为"断言了裸名的价"，
  核对时要单独指出来。

**结论**：§4.5(a) 把 (a) 从"精确命中"改为"模糊命中"**正确**（真实产物证明裸键不存在、重放与归因实验证明落到
`global.anthropic.…-v1:0`）；只需把"测试本身就在证明这一点"降级为"该测试与本轮键集证据相容，但单独看区分不出两种路径"，
并删去 `apac.`。

## 任务 D：过度解读与边界

**D1 「534 键」——原报告的边界已被本轮关闭，但关闭方式要说清**

- 第 8 轮的 534 只来自**脚本重放**，当时未与真实内嵌快照比对（快照当时未生成）。

- 仍然成立的适用边界：其一，该等价结论绑定**这一份** pin 版快照（`6b5e1ee7…`）与这一次构建；

  其二，"键集等价"不等于"行为等价"（见 D3）。

**D2 「3021 重叠」——只是键名集合比较，不宜读作"价格一致"**

- 3021/28 的比较对象是**键名集合**：内嵌快照的顶层键 vs 在线目录里各 provider 的 `models` 键去重集合。
- 两侧**语义并不相同**：内嵌是扁平命名空间（键形如 `anthropic--claude-3-haiku`、`@cf/…`），
  在线是 `provider → models → id` 的层级；去重后做交集，只能说明"同名的 id 仍在目录里"。
- 价格数值、`cost.tiers`、上下文上限、`exactOnly` 标记**一项都没比**（§13.5 自标"部分闭环"，这点是诚实的）。
- 另一条口径边界：比较以在线条目的**键**为准；若某些 provider 的模型键与其 `id` 字段写法不同，交集结果会变。
- 补充事实（本轮实测，供文档参考）：内嵌 models.dev 快照里有 **608 个 `exactOnly: true`** 的键，
  其中 claude 系的 fast/think/@eu/@default 变体占了相当比例——这解释了 §4.5(b) 说的门禁来源。

**D3 重放脚本 ≠ 真实 `find()`：三条未披露的差异**

**D4 「`--mode display` 给 0」的因由是推断，不是实测**

代码层 `Display => cost_usd.unwrap_or(0.0)` 支持"日志无 `costUSD` 时得 0"这一解释，且与实测量值（全零）相符；
但"本机日志确实没有 `costUSD` 字段"这一前提本轮未直接检视（受"不查看会话内容"约束）。应保持"一致解释"档位。

**D5 `--by-agent` 一案的教训（本轮最重要的边界）**

同一选项在**不同入口**下行为相反，正是"只看一个入口就下结论"的典型陷阱。第 8 轮很可能把
`commands::run_daily`（`claude daily` 的路径）当成了顶层 `daily` 的实现，于是把"顶层帮助列出该选项"读成"文档错误"。
核这类问题的正确顺序是：**先确认真实入口**（`accepts_root_all_options` 的四个命令名 + `Command::All`），
**再跑带/不带该标志的对照**，最后才谈"帮助与实现是否一致"。

**D6 单机单时点**

所有运行时结论都建立在"本机 `~/.claude` / `~/.codex` 的当前形态"上。`agents` 键是否出现依赖数据里存在的
agent 种类，换一台机器可能出现不同的键集表现；报告已限定为"结构、字段名与行为"，这一限定应继续保持。
