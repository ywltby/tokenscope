# CCS 历史补充与来源选择交付修复计划

> 执行模型：使用 executing-plans 技能逐项实施。
> 状态：**已实施（2026-11-10，待合并）**；T01–T03 完成，实测对账见 §5；产品发布状态见 §6，不代表用户已安装。

**Goal:** 补齐遗漏的 CCS 来源选择修复，验证会话删除后的已导入历史仍参与统计、重复导入幂等，并明确安装包实际包含哪些修复。

**Architecture:** 复用 PR #56 的桶级三向选择，在当前 main 上整合复验。事实保存、请求身份与统计选择分层；真实数据只读审计，产品查询与导入写入验证使用隔离副本或合成数据。

**Tech Stack:** Rust、SQLite、Vue 3、TypeScript、GitHub Actions。

- PR #56（`dde6d1c`）仍 OPEN、未合并；v0.7.2 的 `report.rs` 仍是二向选择。PR #57 身份修复发布不代表 CCS 三向选择已发布。
- 本机标准安装目录 EXE 和卸载注册项均显示0.7.1，当时无运行中的TokenScope；不据此推断不存在其他安装副本。
- 真实库 `quick_check=ok`。65条Claude日汇总与当前CCS对应记录的请求数、四桶逐条一致，0差异、0缺失；导入批次为旧revision 1。
- 按现有代码与真实库独立核算，61个无明细桶包含24,100次请求、4,337,748,027 token，选择CCS汇总补充。这是只读核算，尚未执行真实副本的产品查询。
- 2026-10-05三个重叠桶：`claude-opus-5-5` 明细133次且四桶逐项不低于汇总；`gpt-6-astra-cc-format` 明细72次、汇总69次、四桶相等；`gpt-6-astra` 两边2次且四桶相等。旧规则两桶报冲突、一桶报替代。
- CCS另有6条Claude汇总未导入；不能直接把其用量之和称为TS缺口，须与已有明细去重和选择。

根因是来源选择缺少“明细已足够，优先明细”分支，以及已有修复漏发。证据不支持“真实数据已被清坏”。

## 2. 设计与不变量

选择复用#56并更新到当前main，不重建统计体系。直接合并过期分支会带入过时版本/发布声明，必须先整合。清库重建、强制重导、逐字段取最大均不采用。

桶键沿用 `(来源自然日, Claude应用, 等价模型)`；现有时区和时间范围限制保持。

| 条件 | 选择与结果 |
| --- | --- |
| 无请求明细 | 用CCS日汇总补历史；源会话删除不影响已导入事实 |
| A：快照范围内明细请求数及四桶均≥汇总（含相等） | 优先明细，汇总不追加；保留项目/时间/请求级费用，不产生未使用汇总的冲突或边界提示 |
| B：明细请求数及四桶均≤汇总且不全等 | 汇总补足该范围，覆盖明细不再重复计入；可信边界之后的新请求照常计入 |
| C：请求数或四桶方向交叉 | 保留明细回退，明确统计冲突类型；不相加、不造差额、不掩盖可能少计 |

- A/B是来源选择策略，数值大小不证明两边是同一请求集合。CCS从会话文件读取，与是否使用路由无关。
- 日粒度费用未知不等于token未计入；不得将汇总伪造成逐请求明细或项目归属。
- 新查询规则必须直接适用于已有导入数据，不要求重导才修复提示。
- 同内容重导不得增加请求/token/事实，不移动批次归属，不伪造旧边界。来源内容改变且用户选择替换时，内容和批次绑定同事务更新。
- 来源删除、停用、重扫不删除历史；保留当前main的Claude/Codex身份修复与幂等性。
- 不扩展/btw、其他agent、自动CCS同步、测试权限或收费规则。

## 5. 实测对账（2026-11-10，真实一致副本）

方法：TS 与 CCS 原库只读打开，经 **SQLite backup API** 取得一致副本（主文件拷贝会丢
WAL）；产品走真实入口 `begin_query → query_summary`（`history_path` 指向副本、来源目录
为空隔离目录——不扫描任何真实会话）；独立核算不经产品选择代码，直接读副本 SQL +
`ModelIdentity` 重算桶键按 §5.1 分类，与产品 `RollupCoverage`/总量互证。全部断言通过后
副本已删除；脱敏证据在 `qa-artifacts/ccs-history-delivery/20261110T004210Z/`
（gitignored，含逐桶计数，不含路径/密钥/对话）。

- **产品 vs 独立核算逐项相等**：无明细桶 61、A 类 3、B 类 0、C 类 0、冲突类型空；
  总量 26,924 请求 / 4,836,837,083 token（input 677,335,514 / output 3,144,641 /
  cache_write 1,381,203,875 / cache_read 2,974,614,053）四桶逐项相等。
- **历史保留**：61 个无明细桶（24,100 请求 / 4,337,748,027 token）全部计入统计，
  与 2026-11-09 只读审计完全一致（差值 0/0/0）；源会话删除不影响这批历史。
- **三个重叠桶（2026-10-05）全部 A 类**，不再误报：
  `claude-opus-5-5` 明细 133 = 汇总 133（明细 token 更大，含请求级信息，选明细）；
  `gpt-6-astra` 两边 2/2、四桶相等（选明细）；
  `gpt-6-astra-cc-format` 明细 72 ≥ 汇总 69、四桶相等（旧规则报“冲突/替代”，新规则
  正确选明细、无伪冲突）。三者均为旧 revision 1 批次（边界不可确认），A 类不产生
  legacy_boundary 披露——与 §5.1“正常选择不弹告警”一致。

- **6 条新汇总不是直接相加**：按桶去重与三向选择后净计入 5 桶 243 请求

  逐项覆盖，按明细统计保留全部请求）。首次导入后产品与独立核算再次逐项相等。
- **65 条已导入日汇总与 CCS 逐字段对账**：请求数、四桶 **0 差异**；
  `input_semantics` 27 行不同（来源 0 → TS 归一化落库 fresh(2)）是写侧归一化的
