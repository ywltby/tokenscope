## 发现与复现

### R01 / P2：批量预览没有维护同一事实的统一终值与全部身份

位置：[history.rs](../../src/history.rs) 的 `classify_batch`（1198 行）、`lookup_event_with_claims`（2333 行）；调用入口为 [ccs.rs](../../src/import/ccs.rs) 的预览批量分类。

模拟表按身份保存独立 `StoredEvent` 副本。更新时仅登记当前写入携带的来源键/来源证据/别名，分配一个新负数 ID；同一已有事实的其他持久身份仍加载数据库旧值。另只有 Insert/Update 登记身份，Unchanged/Conflict/Stale 没有模拟实际提交仍会补记的来源与别名。

本轮新增三个仓库外反例，均使用临时合成库：

1. **实际 CCS 预览→提交链路**：合成两个 Codex proxy 请求 `px-1`、`px-2`，相同 session/raw model/四桶 `100/10/0/0`，时间依次为 `t`、`t+1`。首次导入按现有保守指纹合并为一事实；将 `px-1` 时间改为 `t+2` 后重新预览/提交。预览 `inserted=0, updated=1, unchanged=1, stale=0`；提交 `inserted=0, updated=1, unchanged=0, stale=1`；事实始终为一条。前条更新只进入部分模拟身份，后条通过自己的已有来源键看到旧终值。此例证明预览处置数字错误，**没有证明该路径重复入库或丢失 token**。
2. **直接存储 API，同事实多别名**：既有一条事实持有 `a,b`；第一条写入经 `a` 更新，第二条经 `a,b` 再更新。预览错误报“多个别名指向不同事件”，实际 `write_batch` 更新两次、最终一事实。模拟负 ID 和该事实真实正 ID 被当成不同事实。
3. **直接存储 API，未变化行补别名**：既有事实持有 `a`；第一条内容相同、携带 `a,b`，第二条内容相同、只携带 `b`。预览 `[Unchanged, Insert]`；真实提交 `inserted=0, unchanged=2`、最终一事实。未变化行没有登记新别名，使后条被误分类为新增。

第 2、3 例验证公共存储分类契约；未证明当前每种 CCS 行结构都会构造这些别名组合，不把它们都说成已复现的 GUI 导入故障。三例共同说明“批感知预览与提交完全同构”的完成声明不成立。

剩余修复应让身份引用稳定事实 ID，由事实 ID 保存统一模拟终值，并同步提交各分类的证据登记行为。补预览与提交对账，保留原生优先和已披露的保守指纹限制。

### R02 / P2：N05 内存说明仍沿用旧保留模型，百万构建峰值未测

位置：[stats-semantics.md](../stats-semantics.md) §3.5（259 行及 294 行），[query.rs](../../src/query.rs) 的 `begin_query`（491 行开始流式筛选）；[history_queries.rs](../../tests/history_queries.rs) 的百万测试（283 行）。

说明声称“采集快照整份保留，缩小时间范围不会降低保留量”。当前实现已将事件留在 SQLite，建索引前按 `TimeBounds` 过滤，因此时间范围会减少行索引和记录 ID 的保留量。独立合成探针测得：

| 同一临时历史库 | 命中行数 | 单会话保留记账 |
| --- | ---: | ---: |
| 不限日期 | 1,000 | 93,285 B |
| 仅 2026-10-09 | 500 | 47,813 B |

价格表/来源元数据等固定部分仍存在；该结果不等于整个 RSS、SQLite 页缓存或构建峰值也按相同比例下降。当前代码建议缩小时间范围是有效的，文档应该跟随代码。

新百万测试记录的是预算记账 `query_retained_bytes_for_tests` 与耗时，没有挂分配器或记录构建窗口峰值。旧 `query_memory_budget` 的 400 条峰值测量仍有效，但不能替代 N05 明确要求的百万构建峰值。新测试只检查前两页共 2,000 条；210 条专项确有全量分页断言，4 万条测试只验证汇总和保留量，不能宣称 4 万/百万明细已全部逐页走查。无需以本轮审查新增“必须逐页遍历百万行”的额外要求，但应准确写明现有证据边界。

### R03 / P2：Settings 第一处仍漏掉完整价格候选优先

位置：[Settings.vue](../../frontend/src/views/Settings.vue)（1277 行）。

当前写“同一模型的全部候选按本次请求条件计价后取总费用最高者”。实际规则先排除不完整候选，只在没有完整候选时回退到部分候选。因此“全部候选最高费用”会误导用户，尤其外置高单价但缺分项的候选与完整候选同时存在时。

独立价格探针只读取临时三个价格路径：不完整候选 input=10、缺 output；完整候选 input=1/output=1；请求 input=100/output=10。已知费用分别为 `0.001` 与 `0.00011`，实际正确选择完整候选 `0.00011`，`reason=highest_complete_cost`。这是文案缺口，计价行为符合新计划，不能为迎合文案回退实现。

其余两处旧来源说明已修正；本轮新跨应用与有价分页断言通过，不能继续把这些已补测试列成缺口。
